# Универсальная архитектура формы онлайн-оплаты

Источник требований для `payments-core.mdc`, `payments-frontend.mdc`, `payments-webhooks.mdc`. Копируй в правила только то, что относится к выбранной схеме.

## Поток (для всех провайдеров)

1. Клиент нажимает «Оплатить» → `POST /api/payments` с `orderId` (без суммы).
2. Сервер: загружает заказ, проверяет владельца и статус `pending`, считает сумму, создаёт запись `Payment(status=created)`, вызывает API провайдера с ключом идемпотентности, сохраняет `providerPaymentId`.
3. Сервер возвращает клиенту только то, что нужно виджету: `client_secret` (Stripe), `confirmation_token` (ЮKassa), `PaymentURL` (Т-Банк), `publicTerminalId`+параметры (CloudPayments), `token`/redirect URL (P24, PayU).
4. Клиент отображает виджет/iframe или делает редирект. 3-D Secure и выбор способа оплаты — внутри провайдера.
5. Провайдер шлёт вебхук → сервер проверяет подлинность → идемпотентно обновляет `Payment` и `Order` → отвечает в формате провайдера.
6. Пользователь возвращается на `return_url` → страница показывает «Проверяем оплату…» и опрашивает `GET /api/payments/:id` (или подписка), пока статус не станет финальным. Статус по возврату не меняется.

## Модель данных (минимум)

```
Payment: id (uuid), orderId, provider, providerPaymentId (unique per provider),
  amountMinor (int), currency (ISO 4217), status, idempotencyKey (unique),
  failureReason, rawLastEvent (jsonb, без PAN/CVC), createdAt, updatedAt
WebhookEvent: id, provider, eventKey (unique: provider + event id / paymentId+status),
  receivedAt, processedAt, payload (jsonb)
```

Статусы `Payment`: `created → pending → (requires_action) → succeeded | failed | canceled`; `succeeded → refunded/partially_refunded`. Переходы только вперёд: событие с более ранним статусом после финального игнорируется (вебхуки могут прийти не по порядку и повторно).

## Безопасность и соответствие

- Никогда не принимать, не логировать и не хранить номер карты, CVC, срок действия. Ввод карты — только в iframe/виджете провайдера. Это условие PCI DSS SAQ A.
- С 31.03.2025 (PCI DSS v4.0.1) SAQ A для страниц со встроенным iframe провайдера требует подтвердить, что страница не уязвима к атакам через скрипты: либо меры по требованиям 6.4.3 и 11.6.1 (инвентаризация и контроль скриптов на платёжной странице, обнаружение изменений), либо подтверждение от провайдера, что его решение это обеспечивает (FAQ 1588, https://blog.pcisecuritystandards.org/faq-clarifies-new-saq-a-eligibility-criteria-for-e-commerce-merchants). Для чистого редиректа этот критерий не применяется.
- Практика для платёжной страницы: минимум сторонних скриптов (без аналитики/чатов), строгая CSP с allowlist доменов провайдера, SRI для своих статических скриптов, скрипт провайдера — только с официального домена, не из бандла.
- Секреты (secret key, пароль терминала, CRC, webhook secret) — только в серверных env; в клиент — только публичные ключи. Разные ключи для test/live.
- Только HTTPS (Apple Pay/Google Pay и большинство виджетов не работают по HTTP).
- Ключ идемпотентности: UUID v4 или детерминированный от `orderId`+попытки; хранить в БД и переиспользовать при ретраях. Не использовать email/PII как ключ.
- Вебхук: проверка подписи/HMAC на raw body с constant-time сравнением; при отсутствии подписи (ЮKassa) — allowlist IP и повторный GET статуса у API. Затем дедупликация по `eventKey`, затем бизнес-логика в транзакции. Ответить быстро; тяжёлую работу (письма, выдача) — в очередь.
- Сверять в вебхуке сумму и валюту с `Payment`, а не доверять им слепо.
- Rate limit на `POST /api/payments`, CSRF-защита, авторизация владельца заказа.

## UX и доступность формы

- Кнопка «Оплатить» блокируется после клика (защита от двойного сабмита) + серверная идемпотентность.
- Показывать итоговую сумму и валюту рядом с кнопкой; состояния: загрузка виджета, ошибка инициализации, обработка, успех, отказ с понятной причиной и кнопкой «Попробовать снова» (новая попытка = новый Payment или повтор по правилам провайдера).
- Если собираете свои поля (email, имя, адрес) — `autocomplete` (`email`, `name`, `street-address`, `postal-code`), `inputmode`, видимые `label`, ошибки связаны через `aria-describedby`, фокус на первой ошибке.
- Не вкладывать виджет в свой iframe; при необходимости iframe — `allow="payment *"` (Stripe).
- Мобильная вёрстка, поддержка тёмной темы, локаль виджета = локаль сайта.
- Фискализация (РФ, 54-ФЗ): если нужна — передавать объект чека (`receipt`/`Receipt`) при создании платежа.

## Тест-план (минимум для SPEC.md)

- Успех без 3DS; успех с 3DS; отказ (недостаточно средств, отклонено банком); закрытие виджета; таймаут.
- Двойной клик «Оплатить» → один платёж у провайдера.
- Повтор одного вебхука 2–3 раза → один переход статуса, одно письмо.
- Вебхук с неверной подписью / с чужого IP → 400/403, статус не меняется.
- Вебхуки не по порядку (`succeeded` раньше `pending`).
- Возврат на `return_url` до прихода вебхука → страница ждёт и показывает финальный статус.
- Подмена суммы в запросе клиента → игнорируется.
- Локальная отладка вебхуков через туннель (Stripe CLI `stripe listen`, ngrok/cloudflared для остальных).
